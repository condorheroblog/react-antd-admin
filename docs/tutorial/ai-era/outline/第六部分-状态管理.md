# 第六部分 · 状态管理 — 课题大纲

> 共 2 课（课次 20–21）。状态演变、Zustand 领域划分、持久化与重置设计。

## 第 20 课 · 状态管理演变与 Zustand 域划分

### 学习目标

1. 沿 Redux → Context → Zustand 讲清每代方案的痛点与驱动力。
2. 理解 Zustand 模型：外部 store、选择器订阅、无 Provider。
3. 横向比较当下主流状态库，掌握按领域划分仓库的原则。

### 核心问题

- Redux 样板成本从哪来？RTK 解决了多少？
- Context 为何会性能塌方？
- Zustand 为何不需要 Provider？Jotai/MobX/Valtio 分别适合什么？

### 内容大纲

1. **纵向演进**：Flux/Redux（单向数据流、可预测、样板重）→ Context API（救 props drilling、全量重渲染）→ Zustand（外部 store、切片订阅、零样板）；原子派 Jotai/Recoil 作为并行分支。
2. Zustand API：create/set/get、选择器与相等性、组件外 getState（请求层/守卫为何依赖它）、v5 变化。
3. 本项目六个领域仓库：auth / user / access / tabs / preferences / global；划分原则——同生命周期同变更频率者共处，宁多店不巨无霸。
4. 跨 store 协作：auth.reset 级联 user/access/tabs reset（只调 getState actions）。
5. **横向对比**：
   - Redux Toolkit：生态/调试最强、样板仍多、适合超大型团队；
   - Zustand：极简、学习成本最低、足够覆盖中后台；
   - Jotai：自底向上原子组合、细粒度派生状态；
   - MobX：响应式对象、面向 OOP 心智；
   - Valtio：代理式可变语法；
   - 选型结论与回退条件。

## 第 21 课 · 持久化、命名空间与状态重置设计

### 学习目标

1. 理解 zustand persist 机制与配置取舍。
2. 讲清令牌与身份分库、分策略持久化的安全理由。
3. 设计完整的退出登录归零链路。

### 核心问题

- 什么状态该进 localStorage、什么只配活在内存？
- 同域名多项目存储键冲突怎么办？
- 退出登录只清 token 会留下什么脏状态事故？

### 内容大纲

1. persist 机制：适配器、name、partialize、version/migrate、hydration 时机。
2. 令牌/身份分库：auth 持久化；user/access 内存化（重拉、不信过期身份）；localStorage vs httpOnly cookie 的安全取舍。
3. 命名空间：getAppNamespace + VITE_APP_NAMESPACE 统一前缀。
4. 归零链路：auth.reset → user.reset → access.reset（含 _internalSetRoutes 摘除动态路由）→ tabs.resetTabs；菜单/索引回到 initialState；角落状态审计（通知数/草稿/缓存）。
5. 标签持久化恢复与动态路由重拉顺序。
6. **横向对比**：zustand persist vs redux-persist（黑白名单/版本迁移能力对照）vs 裸写 storage。
