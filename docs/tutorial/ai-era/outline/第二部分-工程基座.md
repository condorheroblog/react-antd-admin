## 第 04 课 · 构建工具演变与 Vite 8 工程初始化

### 学习目标

1. 沿 Webpack → Vite → Rolldown 讲清三代构建方案的演进驱动力。
2. 横向对比当前主流构建工具，说明为什么选 Vite 8。
3. 顺带讲透两个高频选型：包管理器（pnpm）与图标方案（Iconify 双轨）。

### 核心问题

- Webpack 慢的根因？Vite 为什么"秒开"？esbuild+Rollup 双管道的代价？
- 同期主流（Turbopack / Rsbuild / Parcel）各有什么来头与短板？
- 图标方案为什么从精灵图走到 iconfont、再走到 Iconify？

### 内容大纲

1. **纵向演进**：
   - Webpack：一切皆模块、bundle 冷启动，项目越大越慢；
   - Vite 2–7：原生 ESM 免打包开发（esbuild 预构建依赖）+ Rollup 生产包；
   - Vite 8（2026.3）：Rolldown 单一 Rust 打包器，构建提速 10–30 倍，插件 API 兼容。
2. **横向对比**：Webpack 5（存量之王、配置重）、Turbopack（Next 绑定、生态未独立）、Rsbuild（Rspack 系、字节）、Parcel（零配置、生态弱）、Vite 8（生态最大、中立）。
3. 工程初始化（AI 执行、人审查）：pnpm create vite、`type: module`、目录骨架、scripts。
4. **包管理器选型**：纵向 npm → yarn → pnpm/Bun；横向对比幽灵依赖、安装速度、磁盘占用；锁定 `packageManager: pnpm@11`。
5. **图标选型专题**：
   - 纵向：CSS Sprite 精灵图（合并请求）→ iconfont 字体图标（单色、矢量）→ Iconify（20 万+ 图标、按需组件）；
   - 横向：unplugin-icons（Iconify 生态、构建按需）vs 全量引入图标包 vs SVG 内联；
   - 本项目双轨：@ant-design/icons（组件库配套）+ unplugin-icons（Remix Icon 等），vite.config 中 SVG 清洗与 currentColor 处理。
6. 认识 vite.config.ts 整体结构（细节后续课展开）。

### 图表建议（Mermaid）

- `timeline`：构建工具 / 图标 / 包管理器三条演进线。
- `flowchart LR`：图标从源码到 DOM 的按需转换链路。

### 演示要点（HTML 页规划）

- 三代构建架构对比图（内嵌 SVG）。
- 五大构建工具横向对比表（含"被谁主导/绑定谁"一列）。
- 图标三代方案实物小图对比。
- 结论页：选中立生态最大的，不选绑定单一框架的。

### AI 协作点

- 人：工具路线与双轨边界。AI：脚手架、配置、图标注册表。
- 审查清单：版本是否当前大版本？是否误全量引入图标包？

35 分钟。

## 第 05 课 · Vite+：统一工具链时代的到来（新增专课）

### 学习目标

1. 准确理解 Vite+ 是什么、不是什么：统一入口（`vp`），不是框架、不取代 Vite。
2. 纵向理解"手工组装工具链 → 统一工具链"的必然性。
3. 横向对比 Vite+ 与任务运行器/一体化方案，明确本项目当前版本为何暂不迁移、何时该迁移。

### 核心问题

- 一个项目为什么需要 vite、vitest、eslint、prettier、tsup、turbo 等一堆工具？各自配置漂移的代价？
- Vite+ 用一个 `vite-plus` 依赖和九个命令解决了什么？
- 它和 Nx / Turborepo 是竞争关系吗？会不会把项目锁死在 VoidZero 生态？

### 内容大纲

1. Vite+ 背景：VoidZero 团队（Vite/Vitest/Rolldown/Oxc 作者团队）；时间线 alpha 2026.3 → beta 2026.7 → **1.0 于 2026-09-28 发布**。
2. **纵向演进**：石器时代（各工具手工拼装、配置打架）→ 任务运行器时代（Nx/Turbopack 只解决编排）→ 统一工具链（版本作为一个整体被测试后发布）。
3. 九个命令一览：create / install / dev / check（Oxfmt+Oxlint+tsgo）/ test / build / pack（tsdown）/ run（Vite Task，缓存）/ env（Node 版本）。
4. **横向对比**：
   - Vite+ vs 手工组装：少维护 N 份配置、升级一次版本号；代价是采用新入口；
   - Vite+ vs Nx / Turborepo：后者只做编排与缓存，不统一底层工具，可叠加使用；
   - Vite+ vs Create-*-App / UmiJS：不绑定框架、不规定应用结构。
5. 无锁定设计：Vite 插件照常可用、包管理器自由、`vp run` 可跑任意脚本。
6. 与本项目的关系（客观结论）：
   - 本项目当前是"手工组装"（Vite + ESLint + Vitest 各自配置）；
   - 暂不迁移的理由：1.0 刚发布、生态与团队习惯观察期；
   - 迁移路径：`vp migrate`（可把迁移提示词直接交给 coding agent）；触发信号——多仓库配置漂移、CI 提速诉求、新人/AI onboarding 成本。
7. AI 时代视角：Vite+ 官方明确把"标准化人机与 AI 辅助工作流"作为目标。

### 图表建议（Mermaid）

- `flowchart TD`：手工工具栈 vs Vite+ 统一栈的结构对比。
- `sequenceDiagram`：`vp migrate` 在现有 Vite 项目上的迁移过程。

### 演示要点（HTML 页规划）

- "Vite+ 是什么/不是什么"澄清页。
- 九命令矩阵（命令/作用/底层由谁驱动）。
- 三类方案横向对比表。
- 结论页：不是现在必须上，而是必须看懂的下一代方向。

### AI 协作点

- 人：迁移时机决策。AI：执行 vp migrate、收敛配置。
- 审查清单：迁移后 vite 插件是否全部保留？scripts 与 CI 命令是否同步替换？

### 建议时长

30 分钟。

## 第 06 课 · TypeScript 严格化与路径别名

### 学习目标

1. 理解 TS 在中后台中的真正价值：架构契约，而非"给 JS 加类型"。
2. 讲清 tsconfig 关键选项的含义、演变与取舍。
3. 理解 `#*` 路径别名为何要 tsconfig paths + package.json imports 双配置。

### 核心问题

- 为什么要开 `strict`？不开会怎样？
- `moduleResolution: bundler` 是什么？为何不再用 `node`？
- 别名方案众多（`@/` `#/` `~`），本项目为何用 `#*`？

### 内容大纲

1. 类型作为契约：对人是边界文档，对 AI 是最精确的需求约束，对重构是升级保护。
2. **纵向演进**：JS → Flow（Facebook 曾主推）→ TypeScript 胜出；类型检查器新变量：tsc vs tsgo（Go 端口，Vite+ 内置）。
3. tsconfig 关键选项：ESNext + bundler 配套、react-jsx、strict、isolatedModules、skipLibCheck、noEmit。
4. 路径别名：`paths: {"#*": ["./*"]}` + package.json `imports`；`#` 前缀来自 Node 官方子路径导入规范；Vite 运行时解析。
5. 全局类型声明组织。

### 图表建议（Mermaid）

- `flowchart LR`：`#src/...` 从 import 到磁盘文件的解析链（tsc 与 Vite 两条路径）。

### 演示要点（HTML 页规划）

- "类型服务三方：人/AI/重构"图。
- tsconfig 选项分组卡片。
- tsc vs tsgo 速度对比（横向）。
- 结论页：strict 是护栏不是门槛。

### AI 协作点

- 人：严格度与别名规范。AI：生成配置与声明。
- 审查清单：是否滥用 any？是否遵循 import type 与 isolatedModules？

### 建议时长

25 分钟。

## 第 07 课 · 工程规范与护栏：ESLint、Git Hooks、依赖升级与循环依赖检查

### 学习目标

1. 理解规范要"自动执行"而非靠文档约定；讲清 ESLint 配置演变并与 Biome / Oxlint 横向比较。
2. 彻底搞懂 Git 提交的两道钩子：`pre-commit` 与 `commit-msg`，以及 simple-git-hooks + lint-staged + commitlint 的协作。
3. 掌握两项工程健康检查：用 taze 跟进依赖大版本、用 circular-dependency-scanner 检查循环依赖。

### 核心问题

- Flat Config 解决了旧配置什么问题？Prettier 为什么退场？
- 为什么规范必须挂到 Git Hooks 上才能真正生效（包括 AI 生成的代码）？
- `pre-commit` 和 `commit-msg` 分别拦什么？顺序如何？
- 依赖越积越旧、模块互相引用成环，如何用工具提前发现而不是等线上出问题？

### 内容大纲

#### A. 代码规范（ESLint）

1. 规范三层：语法（TS）→ 质量与风格（ESLint）→ 提交信息（commitlint）。
2. **纵向演进**：JSHint → ESLint（`.eslintrc` 层级嵌套）→ ESLint 9+ Flat Config（扁平数组、显式导入）。
3. **横向对比**：
   - ESLint 10 + @antfu/eslint-config：规则生态最全、零 Prettier（Stylistic 收敛风格）；
   - Biome：Rust 全家桶（lint+format），速度快但规则覆盖仍在追赶；
   - Oxlint：50–100 倍速、600+ 兼容规则，随 Vite+ GA，适合过渡期/CI 加速；
   - 选型结论：规则完备度优先 → ESLint；切换信号是规则覆盖满足 + 工具链统一诉求。

#### B. Git 提交护栏（pre-commit 与 commit-msg）

4. 为什么用 Git Hooks：规范文档可以被无视，钩子是提交前的强制闸门，对人和 AI 一视同仁。
5. **simple-git-hooks**：
   - 零依赖、把钩子写进 `.git/hooks`；为什么不选 husky（更轻、无需额外安装层）；
   - `prepare: simple-git-hooks` 脚本：`pnpm install` 后自动注册钩子；
   - package.json 中两个钩子的配置——`pre-commit` 与 `commit-msg`。
6. **pre-commit 钩子**：执行 `npx lint-staged`。
   - lint-staged 的意义：只对暂存区文件跑 ESLint，而非全仓库，速度快；
   - 配置 `"*": ["eslint --fix"]`：提交前自动修复，修不好则阻断提交。
7. **commit-msg 钩子**：执行 `npx commitlint --edit`。
   - commitlint 校验提交信息，继承 `@commitlint/config-conventional`；
   - Conventional Commits 格式：`type(scope): subject`；
   - 本项目 type-enum 全表：feat/fix/perf/style/docs/test/refactor/build/ci/chore/revert/wip/workflow/types/release；
   - 关键规则：header 最长 108、subject/type 不可为空、body 前需空行；
   - 价值：提交历史可检索、可自动生成 changelog、支撑语义化版本。
8. **两道钩子协作**：pre-commit 管"代码内容"，commit-msg 管"提交说明"；前者先跑、失败则后者不执行。

#### C. 依赖与依赖结构健康检查

9. **taze 升级依赖**：
   - 解决的痛点：package.json 版本号常年落后、不敢升级；
   - `npm-check: taze major -lrw`：递归检查子目录、拉取最新大版本、写回 package.json 并自动安装；
   - taze.config.js 的 recursive / force / write / install 逐项说明；
   - 安全节奏：小版本常规跟进、大版本分批迁移并对照 migration 文档，配合第 27/28 课的版本演进机制。
10. **circular-deps 检查循环依赖**：
    - 循环依赖为什么是慢性病：初始化顺序不确定、打包产物异常、重构困难；
    - `check:circular-deps: ds src --output circular-deps.json`，基于 circular-dependency-scanner；
    - 产物解读：如何从报告定位成环链路，用依赖倒置 / 抽公共模块解环；
    - 建议接入 CI（呼应第 27 课），让新增成环在合并前被拦截。

- `flowchart LR`：模块 A↔B 成环 → 抽取公共层 C 的解环示意。

### AI 协作点
