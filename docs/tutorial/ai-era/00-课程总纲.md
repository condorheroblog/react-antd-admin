## 一、课程定位

这不是一门教你"写代码"的课。

在 AI 可以根据一句需求生成完整页面的时代，**代码实现的边际成本趋近于零，架构决策的价值被急剧放大**。同样一个需求，AI 能给出十种写法，选哪一种、为什么选、它和主流方案差在哪、未来半年会不会被版本淘汰——这些问题 AI 不会替你负责。

本课程基于本仓库（一个持续跟进社区最新版本的 React 中后台模板），带你站在**架构选型与框架搭建**的高视角，完整走一遍企业级中后台系统的设计过程。

### 与传统教程的区别

| 维度         | 传统教程           | 本课程                                 |
|--------------|--------------------|----------------------------------------|
| 重心         | API 讲解、逐行实现  | 选型决策、分层设计、演进背景             |
| 代码         | 老师写、学生抄      | AI 生成，学生负责描述需求与审查         |
| 典型问题     | "这个 API 怎么用？" | "为什么用它而不是主流的别的？边界在哪？" |
| 版本观       | 回避版本问题       | 纵向演进 + 横向对比作为核心线索        |
| 学完后的能力 | 能照着写           | 能做决策、能审查 AI、能搭框架            |

### 适合谁学

- 已掌握 **React 基础**（组件、props/state、Hooks 的常规用法）
- 具备 **JavaScript / HTML / CSS 基础知识**
- 不需要你用过 TypeScript、Vite、antd——但需要你愿意接受"先理解设计，再让 AI 补实现"的学习方式

### 不适合谁

- 完全零基础、需要从零讲 JS 语法和 React 概念的学习者
- 希望逐行背诵 API、通过模仿记忆掌握框架的学习者

## 二、课程设计原则

1. **重设计，弱实现**：每节课先讲清楚"要解决什么问题、有哪些方案、为什么选这个方案"，具体实现交给 AI 生成并由你审查。
2. **纵向演进 × 横向对比（核心方法论）**：每个技术选型都从两个维度展开——
   - **纵向演进（时间轴）**：它从哪一代方案演变而来？上一代解决了什么、又留下了什么痛点？为什么必然走到今天这一步？
     - 例：图标 `精灵图 → iconfont 字体图标 → Iconify 按需图标`；请求 `XHR → jQuery $.ajax → axios → fetch → ky`。
   - **横向对比（同一时刻的主流候选）**：当下主流方案有哪些？它们各自的适用场景与代价是什么？为什么本项目选了当前这一个？
     - 例：HTTP 客户端在 `axios / ky / ofetch` 之间怎么选；状态管理在 `Redux Toolkit / Zustand / Jotai` 之间怎么选。
3. **一切取舍有依据**：不出现"官方推荐所以用"这类结论，只讲约束条件下的权衡；并明确"什么情况下应该改选别的"。
4. **一体两用**：每节课产出一份 Markdown 教程（学生自学 / 老师讲义）+ 一份 HTML 演示（课堂投屏，浓缩精华）。
5. **AI 协作显性化**：每节课明确划分"人必须做的决策"与"可以交给 AI 的实现"，并给出与 AI 协作的提示思路与审查清单。

## 四、课程地图（8 部分 · 28 课）

### 第一部分 · 导论与选型（3 课）

建立"AI 时代设计优先"的认知框架，俯瞰中后台系统的能力模型，理解整套技术栈的选型逻辑。

| 课次 | 课题                                           | 核心命题                            |
|------|------------------------------------------------|-------------------------------------|
| 01   | AI 时代的中后台开发：为什么实现贬值、设计升值    | 开发者的价值迁移到哪里？             |
| 02   | 成品项目预览：中后台系统的能力模型              | 一个"完整"的中后台到底包含哪些能力？ |
| 03   | 技术选型决策：React 19 生态全家桶是怎么选出来的 | 选型决策框架、纵向/横向双维方法论    |

### 第二部分 · 工程基座（4 课）

从空目录到可开发的工程：构建工具演变、Vite+ 统一工具链、TypeScript 架构契约、代码规范与提交工作流。

| 课次 | 课题                                                   | 核心命题                                                                 |

## 五、每课交付物规范

### 5.1 两个文件，一体两用

每节课最终产出两个同名文件：

1. **教程 Markdown（`.md`）**：完整知识载体——学生阅读自学，老师作为讲义。
2. **演示 HTML（`.html`）**：Markdown 的结构化浓缩——课堂投屏，类似 PPT；只保留核心观点、对比表、架构图、结论，不展开论述。

### 5.2 目录约定

```text
docs/tutorial/ai-era/
├── 00-课程总纲.md                 # 本文件
├── design/
│   └── HTML演示风格规范.md        # 全部 HTML 的审美与模板唯一标准
├── outline/                       # 第一阶段：各部分大纲（当前审阅对象）
│   ├── 第一部分-导论与选型.md
│   └── …
└── lessons/                       # 第三阶段：每课成品
    ├── 01-ai-era-dev/
    │   ├── 01-ai-era-dev.md       # 教程 / 讲义
    │   └── 01-ai-era-dev.html     # 演示（遵循 design/HTML演示风格规范）
    └── …
```

> 文件 slug 使用英文 kebab-case；中文标题写在文件内。如你有命名偏好，审阅时指出。

### 5.3 Markdown 教程统一结构

```text
# 课题标题
- 学习目标（3 条以内）
- 这节课要回答的核心问题
- 纵向演进（上一代方案 → 痛点 → 本代方案，配 Mermaid timeline/flowchart）
- 横向对比（当下主流候选方案对比表 + 各自适用场景与代价）
- 选型结论：为什么选当前方案？什么情况下应该改选别的？
- 架构落地（配合本仓库真实代码位置，代码以"读懂"为度）
- AI 协作点（人做的决策 / AI 做的实现 / 审查清单）
- 小结
- 思考题与拓展（官方文档、changelog/migration 入口）
```

### 5.4 Mermaid 图表使用约定

涉及逻辑、路径、技术演进时，Markdown 中统一使用 Mermaid：

| 表达内容               | 图类型                       | 典型课   |
|------------------------|------------------------------|----------|
| 技术代际演进           | `timeline` 或 `flowchart LR` | 04/16/20 |
| 启动/请求路径、数据流向 | `flowchart TD/LR`            | 08/17/19 |
| 守卫、缓存状态          | `stateDiagram-v2`            | 14/15/18 |
| 登录、刷新、退出时序     | `sequenceDiagram`            | 13/14/21 |
| 模块依赖关系           | `graph` / `flowchart`        | 02/22    |

约定：图内文字精炼（不写整句）；同一文档配色与方向保持一致；复杂图拆分为多张小图。

### 5.5 HTML 演示风格

全部 HTML 的审美、Token、版式与代码模板以 [HTML演示风格规范.md](file:///Users/david/i/react-antd-admin/docs/tutorial/ai-era/design/HTML演示风格规范.md) 为**唯一标准**。要点：

- 单文件、零外部依赖，双击可开；16:9 自适应，← →/空格翻页；
- 克制、专业、信息优先的工程师审美：1px 描边、留白、单层轻阴影，拒绝玻璃拟态与发光堆砌；
- 明/暗双主题跟随系统；统一品牌色、字体、间距、圆角；
- HTML 内图表一律使用**内嵌 SVG**（不内联 Mermaid 运行时），线条/配色遵循规范。

### 5.6 内容红线

- 不逐行教手写实现，实现通过"给 AI 的需求描述 + 审查要点"呈现；
- 不虚构 API 与版本事实，关键结论以官方文档 / changelog 为准；
- 横向对比保持客观：主流落选方案讲清其适用场景，不做贬低式描述；
- 不与本目录下原有的非 AI 时代资料产生内容耦合。
